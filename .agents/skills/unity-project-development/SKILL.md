# Unity 项目开发

在符合仓库现有架构的前提下，完成范围最小但功能完整的改动。以当前代码、asmdef、项目设置和工作区状态为事实来源。

## 工作流程

1. 编辑前先检查。
   - 检查工作区，保留用户无关的已有改动。
   - 阅读目标文件、附近的协作代码、所属 asmdef 和相关包元数据。
   - 在决定代码归属或修改依赖前，阅读 [references/project-map.md](references/project-map.md)。
2. 将改动放到正确的归属层。
   - 可复用的第一方运行时代码和编辑器代码放入对应的嵌入式 `com.lxy.*` 包。
   - 场景、Prefab、配置、项目生成产物和游戏内容放在 `Assets` 下。
   - 编辑器 API 必须放在 `Editor` 目录或仅限 Editor 的程序集内。
3. 保护程序集边界。
   - 保持文档规定的依赖方向。
   - 只有真正需要跨边界共享时，才把稳定契约放入 `Game.Contracts`。
   - 不得让 AOT 启动程序集直接依赖仅存在于热更新程序集中的具体类型。
   - 除非功能确实需要新的编译期依赖，否则不要修改 asmdef。
4. 收敛实现范围。
   - 有意识地使用 Unity 生命周期；订阅、资源句柄和创建的对象必须有对应清理。
   - 在热路径中避免逐帧分配、重复组件查找、LINQ、字符串拼接和不必要的 Instantiate/Destroy。
   - 除非需求包含迁移，否则保留序列化字段名和 `.meta` 标识。
   - 遵循现有异步/协程的错误传播和取消约定。
   - 当供应商代码或生成产物由源设置、生成器管理时，不要手工修改生成结果。
5. 按风险比例验证。
   - 检查最终差异，并搜索所有被修改 API 的引用。
   - 编译或测试可用范围内最小的受影响程序集或 Unity 工作流。
   - 相关时验证生命周期清理、失败路径和序列化敏感改动。
   - 如果仍需 Unity Editor 或目标 Player 验证，必须明确说明。

## 审查输出

先报告真实的正确性问题，再给出风格建议。说明问题对 Unity 或项目的具体影响，引用受影响路径，并提供范围明确的修复方案。不要重构无关代码。
